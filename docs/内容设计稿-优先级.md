### 1.3 数据驱动抓到的三个玩法缺陷 `[实测]`

平衡对拍工具第一次跑就暴露了三个**靠读代码看不出来**的缺陷：

1. **地图固定层被当成随机层**：`_generate_layer` 判 `type == 'fixed'`，而模板里根本没有这个值 → 九层全走随机分支 → 第 8 层的最终 Boss 变成普通小怪、宝藏密室不存在、第 1 层不是营地。
2. **通关不可达**：`current_layer` 到 9 封顶，`floor > MAX_FLOORS` 永不成立，`VictoryScene` 没有任何入口。
3. **术士完全无法购买**：`RecruitSystem.recruit` 把「生命分流」判定放在购买之前并直接 `return`，只要血量够就买不到任何东西（场上单位 3.6 vs 其他职业 7.0）。

> 结论：**先把"能测"做出来，再谈加内容。** 这三条都不是内容不足，而是"游戏其实玩不通"。

## 2. 硬约束（写进仓库、由测试看住）`[实测]` + `[调研]`

| 约束 | 依据 | 承载体（门禁/测试） |
| --- | --- | --- |
| 全局关键词词表 **≤ 18 个**，每个关键词 **≥ 4 个承载单位** | Hearthstone 策划 Ben Brode 的判据：一个关键词只允许表达一条规则，且只有 2-3 张卡用它时不该起名 `[调研]` | `test_every_keyword_has_enough_carriers` |
| **每个种族每个星级 ≥ 2 个单位** | 2/4/6 共鸣要组得出来；档位上限应满足「最高档 ≤ 该共鸣单位数 − 2」`[调研]` | `test_every_tribe_has_two_units_per_tier` |
| 战斗结算**只允许既有 7 种事件类型**（battle_start / turn_start / attack / death / heal / summon / trigger_keyword），不新增阶段 | 新关键词必须能挂在既有管线与事件上，否则会牵动 UI 动画解析与平衡 | `tests/test_battle_engine.py`（关键词用例） |
| 数据契约有**唯一登记处**：关键词 → `KNOWN_KEYWORDS`、宝物效果 → `RELIC_EFFECT_HANDLERS`、事件效果 → `SUPPORTED_EFFECT_KEYS` | 本仓历史教训：数据里写了、引擎里没实现（25 件宝物里 4 个效果无人调用） | `tests/test_data_integrity.py` 三个登记校验 |
| 数据交叉引用必须成立（事件引用的敌人、宝物效果、脚本类型） | 事件引用 `mimic` 而敌人不存在，战斗直接断链 | `test_event_battle_targets_exist` 等 |

**关键词三轴分类法**（用来"造新单位"而不是"造新关键词"）`[调研]`：
- 触发时机：战吼 / 亡语 / 战斗开始 / 回合开始 / 受击 / 攻击 / 击杀 / 光环
- 作用对象：自身 / 相邻 / 全体友方 / 随机 N / 最低血量友军 / 全体敌人
- 效果类型：伤害 / 增益 / 护盾 / 治疗 / 召唤 / 经济 / 词条赋予

`8 × 6 × 7` 的组合里有几百个格子，而全池只有 74 个单位 —— **换轴组合就是新单位，这比新增关键词更能"低价换新鲜感"**。

## 4. 档 2（本轮已落地）：用「组合数」换重复可玩性

核心思路：**内容量 = 池子大小 × 组合数**。同一条命的中期收益远高于加 10 个同质随从。

| # | 内容 | 依据 | 验收方式 |
| --- | --- | --- | --- |
| 2.1 | **精英/Boss 词缀系统**：6 条词缀（狂暴/重甲/淬毒/疾行/巨型/不灭），第 5 层起精英带 1 条、Boss 带 2 条；进阶 ≥3 再多 1 条 | "池 + 词缀"是 Boss 变化里性价比最高的方案（5 Boss × 6 词缀 = 35 种遭遇，美术成本只多几个图标）`[调研]` | `test_elite_affixes_start_at_layer_five`、`test_boss_takes_two_affixes_and_advancement_adds_one` |

## 6. 验收阈值：把设计变成可跑的门禁

### 6.1 平衡阈值 `[调研]` + `[实测]`

| 指标 | 目标 | 采集方式 |
| --- | --- | --- |
| 首次通关率（前 5 局至少赢一次） | ≥ 60% | 需要埋点：按 `total_runs <= 5` 分桶统计 `victories` |
| 长期通关率（普通难度） | 25-40% | `tools/balance_report.py`（当前 42.2%，略高于上限；进阶 5 = 26.7%） |
| 平均到达层数 | 5.5-6.5 | 同上（当前 7.49，偏高 → 前中期还需要加压） |
| 分层战斗胜率 | 1-3 层 80-85% / 4-6 层 65-75% / 7-9 层 50-60% | 需给 `balance_report` 加分桶输出 |
| 职业间通关率极差 | ≤ ±8pp | 同上（当前 32.5↔52.5，**未达标**，见档 3 的 P1-1） |
| 宝物/事件选择率 | 单件宝物被拿 ≤60%、≥8%；事件单选项被选 ≤70% | 需要埋点：`run_history` 已存 `relics` 与 `stats`，事件选项需新增字段 |

**对拍方法（已落地）**：
```bash
python tools/balance_report.py --runs 40 --ab     # 目标选择 A/B 对照
python tools/balance_report.py --advancement 3    # 指定进阶
```
固定种子 + 分层统计 → 任何数值改动的效果都可量化，避免"改完感觉差不多"。

### 6.2 需要在下一轮补的埋点

`persistence.record_run` 已经记录 `stats`（battles/battle_wins/elites/bosses）与 `seed`；
下一轮建议补：`relics_offered`（三选一时被提供了什么）、`event_choice`（事件选了哪个选项）、
`death_cause`（死于哪个敌人/哪一层）。有了这三项，"哪件宝物从没被拿过、哪个事件从没被选过"就能直接查。
